## Iteration US-196 - Fri, Apr 14, 2026

Completed: Integrate channel manager for live OTA availability synchronisation (ID: US-196)

### What was implemented
- **Beds24 client** (`site/src/lib/beds24-client.ts`):
  - Implemented `parseAvailabilityResponse()` to parse real Beds24 API responses
  - Returns proper `ChannelManagerAvailability` objects with room inventory
  - Graceful fallback to placeholder data when channel manager is not configured
- **ARI endpoint** (`site/src/app/api/ari/route.ts`):
  - Fetches live availability from Beds24 API
  - Maps to standard ARI format for connectivity partners (Google Free Booking Links)
  - Returns JSON with property info, rooms, rates, and booking URL
- **Booking sync endpoint** (`site/src/app/api/bookings/sync/route.ts`):
  - Accepts POST requests with booking details (checkin, checkout, guest info, room type)
  - Syncs bookings to Beds24 to close availability across OTAs
  - Includes availability check via GET with query parameters
- **Webhook endpoint** (`site/src/app/api/webhooks/beds24/route.ts`):
  - Processes Beds24 webhook events for availability updates, booking creation/cancellation
  - Validates webhook signature using HMAC-SHA256
  - Logs event details (extensible for database updates)
- **Configuration & types**:
  - Channel manager config with environment variables
  - Type definitions for availability, bookings, webhooks
  - Updated .env.local.example with all required secrets

### Patterns discovered
- Next.js App Router uses async GET/POST functions
- Beds24 API response structure uses `roomtypes` key with room availability objects
- Response parsing should handle multiple field names (id/roomId, name/roomName) for flexibility
- Placeholder data allows testing without configured channel manager

### Gotchas
- Beds24 API field names vary (id vs roomId, total vs totalInventory)
- Parser must be defensive and return empty array on malformed responses
- Webhook validation using HMAC requires exact payload matching (must use `request.text()` not `request.json()`)

- Webhook endpoint: ✓ shows as dynamic route (ƒ)

## Pre-analysis for US-196 (Gemini 2.5 Pro)
This user story is for a hotel channel manager integration, which seems mismatched with the `lhdn_payroll_integration` app context. The following brief assumes the target is a hospitality-focused Frappe app (e.g., `pelangi_hospitality`).

**Project:** US-196: Channel Manager Integration
**Target App:** `pelangi_hospitality` (Assumed)

**1. Python Files to Modify:**
*   **New File:** `pelangi_hospitality/api/channel_manager.py` to encapsulate all communication with the third-party channel manager API (e.g., Beds24).
*   **New File:** `pelangi_hospitality/api/webhooks.py` to create a dedicated, whitelisted endpoint to receive incoming ARI updates and bookings from the channel manager.
*   **Existing File:** `pelangi_hospitality/doctype/booking/booking.py` (or similar for reservations) to add logic that pushes new bookings to the channel manager.

**2. Frappe DocTypes & Hooks:**
*   **DocTypes:**
    *   A new singleton `Channel Manager Settings` DocType is needed to store API keys, endpoint URLs, and credentials.
    *   The `Booking` DocType will require modification to trigger syncs and store the channel manager's external booking ID.
    *   The `Room` DocType needs a field to map its ID to the corresponding ID in the channel manager.
*   **Hooks (`hooks.py`):**
    *   `on_submit` on the `Booking` DocType to call `channel_manager.py` and reduce availability.
    *   `on_cancel` on the `Booking` DocType to call `channel_manager.py` and increase availability.

**3. Implementation Approach:**
1.  Implement the API client with methods for fetching and updating availability.
2.  Use the `Booking` DocType's server-side `after_insert` and `on_trash` events to trigger API calls.
3.  Create a whitelisted API endpoint for the website frontend to call, which in turn fetches live availability from the channel manager API.
4.  Implement the webhook endpoint to create/update local `Booking` documents from incoming OTA bookings.

**4. Edge Cases & Gotchas:**
*   **Race Conditions:** Implement a locking mechanism or re-verify availability with the channel manager API just before creating a booking to prevent overbookings.
*   **API Failure:** Use Frappe's background jobs (RQ) with a retry mechanism for all outgoing API calls to handle transient network issues or API downtime.
*   **Webhook Security:** Validate incoming webhooks using a shared secret to prevent unauthorized requests.
